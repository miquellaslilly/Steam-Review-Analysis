# ТЕХНИЧЕСКОЕ ЗАДАНИЕ
## Разработка экспериментальной системы аспектного анализа тональности пользовательских отзывов Steam на основе кластеризации и классификации текстов

## 1. Общая информация о проекте

### 1.1. Назначение проекта

Необходимо разработать программную систему для проведения исследовательских экспериментов в области компьютерной лингвистики и анализа текстов.

Система должна обеспечивать сбор, предварительную обработку и анализ пользовательских отзывов о компьютерных играх с платформы Steam.

Основная задача — исследовать возможность перехода от традиционного анализа общей тональности отзыва к более детальному аспектному анализу, позволяющему определять:

- общую тональность отзыва;
- отдельные аспекты игры, упоминаемые пользователем;
- конкретные объекты эмоционального отношения (персонажи, игровые механики, сюжетные элементы и другие сущности);
- причины положительной или отрицательной оценки;
- информативность и пригодность отзыва для дальнейшего анализа;
- взаимосвязь между содержанием отзыва, общей рекомендацией игры и количеством проведённых в ней часов.

Проект предназначен для проведения научного исследования. Основным результатом является не готовый коммерческий продукт, а экспериментальная реализация методов, получение количественных результатов и возможность их дальнейшего анализа.

### 1.2. Основная исследовательская идея

Традиционная классификация тональности определяет эмоциональную оценку всего отзыва, не учитывая, что пользователь может положительно оценивать одни характеристики игры и отрицательно — другие.

Например:

"The game is amazing. Great gameplay, beautiful graphics and interesting story. But I cannot recommend it because of the new microtransactions."

В данном случае:
- общая рекомендация Steam: отрицательная;
- игровой процесс: положительная тональность;
- графика: положительная тональность;
- сюжет: положительная тональность;
- монетизация: отрицательная тональность;
- причина отрицательной рекомендации: введение микротранзакций.

Система должна уметь выявлять подобные противоречия между общей рекомендацией и локальной тональностью отдельных аспектов.

Главная идея исследования — определять не только эмоциональную оценку пользователя, но и то, на какие характеристики игры она направлена и чем обусловлена.

## 2. Цель и задачи исследования

### 2.1. Цель

Разработка и экспериментальная оценка комбинированного подхода к аспектному анализу тональности пользовательских отзывов Steam на основе кластеризации текстовых представлений, классификации тональности и извлечения объектов эмоционального отношения.

### 2.2. Основная исследовательская гипотеза

Разделение пользовательских отзывов на тематические аспекты с последующим определением тональности отдельных фрагментов и извлечением объектов эмоционального отношения позволяет выявлять конкретные факторы, связанные с положительной и отрицательной оценкой компьютерных игр, которые невозможно установить при классификации отзыва целиком.

### 2.3. Дополнительные гипотезы

H1. Фильтрация малоинформативных и нерелевантных отзывов улучшает качество выявления аспектов и определения причин пользовательской оценки.

H2. Общая отрицательная рекомендация может сочетаться с преимущественно положительной тональностью отдельных аспектов игры.

H3. Продолжительность игрового времени связана с тематикой и характером пользовательских оценок.

H4. Анализ на уровне предложений и смысловых фрагментов позволяет точнее определять локальную тональность, чем классификация целого отзыва.

### 2.4. Задачи

1. Получить корпус пользовательских отзывов Steam.
2. Провести анализ структуры и качества исходных данных.
3. Реализовать предварительную обработку текстов.
4. Разработать механизм оценки информативности отзывов.
5. Реализовать векторизацию текстовых представлений.
6. Провести кластеризацию для автоматического выявления тематических аспектов.
7. Интерпретировать полученные кластеры и присвоить им содержательные названия.
8. Реализовать классификацию тональности отдельных аспектов и текстовых фрагментов.
9. Реализовать извлечение конкретных объектов эмоционального отношения.
10. Определять причины положительной и отрицательной оценки.
11. Исследовать связь между общей рекомендацией Steam и тональностью отдельных аспектов.
12. Исследовать влияние игрового времени на содержание и тональность отзывов.
13. Реализовать детекцию новых или ранее не встречавшихся аспектов.
14. Провести сравнительные эксперименты и сформировать результаты для научной статьи.

## 3. Исходные данные

### 3.1. Источник данных

Основной источник — пользовательские отзывы платформы Steam.

Для получения данных использовать официальный Steam Store Reviews API либо другой допустимый публичный источник данных.

Сбор должен поддерживать возможность выбора игры по App ID.

На первом этапе необходимо использовать одну игру с достаточным количеством пользовательских отзывов и разнообразной пользовательской реакцией.

Архитектура должна предусматривать возможность последующего подключения других игр без изменения основной логики обработки.

### 3.2. Необходимые поля

Для каждого отзыва желательно получить следующие данные:

| Поле | Назначение |
|---|---|
| review_id | Уникальный идентификатор отзыва |
| app_id | Идентификатор игры |
| review_text | Текст отзыва |
| recommended | Общая рекомендация Steam (положительная/отрицательная) |
| playtime_at_review | Количество часов на момент написания отзыва |
| playtime_forever | Общее игровое время на момент сбора данных |
| timestamp_created | Дата создания отзыва |
| timestamp_updated | Дата обновления отзыва |
| language | Язык отзыва |
| voted_up | Признак положительной рекомендации, если доступен |
| votes_up | Количество положительных голосов за отзыв |

Обязательными для основного исследования являются:
- текст отзыва;
- идентификатор игры;
- общая рекомендация;
- идентификатор отзыва.

Игровое время и остальные поля использовать как дополнительные признаки.

Приоритет отдавать playtime_at_review, поскольку playtime_forever может включать время, проведённое после публикации отзыва.

Если историческое игровое время отсутствует, не подменять его текущим без явного указания в данных и последующем анализе.

### 3.3. Объём данных

Рекомендуемый объём:
- минимальный экспериментальный корпус: 5 000 отзывов;
- предпочтительный объём: 10 000–30 000 отзывов;
- при наличии ресурсов допускается увеличение корпуса.

Количество отзывов должно определяться реальной доступностью данных и возможностями API.

Необходимо предусмотреть:
- пагинацию;
- обработку ограничений API;
- повторные запросы при временных ошибках;
- исключение дубликатов;
- сохранение промежуточных результатов;
- возможность продолжить сбор после прерывания.

### 3.4. Язык отзывов

Основной эксперимент желательно проводить на англоязычных отзывах, поскольку значительная часть доступных NLP-моделей и инструментов поддерживает английский язык.

Архитектура должна позволять расширить исследование на другие языки.

Необходимо сохранять оригинальный текст отзыва независимо от применяемой предобработки.

## 4. Архитектура системы

Система должна состоять из независимых модулей.

### Модуль 1. Сбор данных

Функциональность:
- получение отзывов Steam;
- фильтрация по App ID;
- настройка количества загружаемых отзывов;
- сохранение исходных данных;
- контроль полноты загрузки;
- исключение дубликатов.

Результат: исходный датасет.

### Модуль 2. Предварительная обработка

Необходимо реализовать:
- определение языка;
- очистку HTML и служебных символов;
- обработку ссылок;
- нормализацию пробелов;
- обработку пустых отзывов;
- выявление дубликатов;
- токенизацию;
- удаление стоп-слов;
- лемматизацию при необходимости;
- сегментацию отзывов на предложения.

Важно: не удалять отрицания, эмоционально значимые слова и игровые термины.

Следует сохранять две версии текста:
1. Оригинальный текст.
2. Обработанный текст.

Для моделей на основе BERT/Sentence-BERT использовать текст с минимальной очисткой, чтобы не потерять контекст.

### Модуль 3. Определение информативности отзывов

Необходимо разработать механизм определения того, насколько отзыв пригоден для выявления конкретных аспектов и причин пользовательской оценки.

Предусмотреть три класса:

1. Высокая информативность.
2. Средняя информативность.
3. Низкая информативность.

Примеры:

Высокая:
"After the latest update, the game crashes every time I try to load a save."

Средняя:
"The combat system is boring and repetitive."

Низкая:
"Bad game."

Отдельно предусмотреть выявление:
- спама;
- бессвязных текстов;
- повторяющихся сообщений;
- нерелевантных отзывов;
- отзывов без содержательной оценки игры.

Важные требования:

1. Не использовать исключительно длину отзыва для определения информативности.
2. Короткий отзыв может быть информативным, если содержит конкретную проблему.
3. Не смешивать тональность и информативность.
4. Не удалять низкоинформативные отзывы из исходного корпуса.

Для оценки информативности необходимо предусмотреть ручную разметку части корпуса и обучение классификатора.

Минимальная выборка для ручной разметки — 200–300 отзывов.

Разметка должна содержать:
- класс информативности;
- наличие конкретного аспекта;
- наличие конкретной причины оценки;
- наличие спама или нерелевантного содержания.

Провести эксперимент с двумя вариантами:
- анализ всего корпуса;
- анализ только отзывов средней и высокой информативности.

Сравнить полученные результаты.

### Модуль 4. Векторизация текстов

Реализовать возможность сравнения нескольких способов представления текстов:

1. TF-IDF.
2. Word2Vec.
3. Sentence-BERT или другая подходящая модель семейства BERT.

Основной метод для семантической кластеризации — Sentence-BERT.

TF-IDF и Word2Vec использовать для сравнительного эксперимента.

Векторизация должна поддерживать обработку:
- отдельных отзывов;
- предложений;
- смысловых фрагментов.

Необходимо обеспечить возможность сохранения готовых эмбеддингов для повторного использования без повторного вычисления.

### Модуль 5. Кластеризация и выявление аспектов

Основная задача — автоматическое выявление тематических аспектов пользовательских отзывов без использования общей рекомендации Steam в качестве признака кластеризации.

Реализовать:
- K-Means;
- DBSCAN.

Для K-Means предусмотреть подбор количества кластеров с использованием:
- метода локтя;
- Silhouette Score.

Для DBSCAN предусмотреть подбор параметров eps и min_samples.

Оценивать:
- Silhouette Score;
- количество сформированных кластеров;
- количество некластеризованных объектов;
- размеры кластеров;
- устойчивость результатов.

ARI использовать только при наличии соответствующей эталонной разметки.

Для интерпретации кластеров реализовать:
- извлечение ключевых слов через TF-IDF;
- определение наиболее характерных словосочетаний;
- просмотр репрезентативных примеров;
- возможность присвоения содержательных названий кластерам.

Ожидаемые типы аспектов:

- сюжет;
- персонажи;
- игровой процесс;
- игровые механики;
- графика;
- звуковое оформление;
- производительность;
- технические ошибки;
- оптимизация;
- монетизация;
- обновления;
- мультиплеер;
- сложность;
- управление;
- реиграбельность.

Перечень не должен быть жёстко зафиксирован в алгоритме. Необходимо допускать обнаружение новых тематических групп.

### Модуль 6. Извлечение объектов эмоционального отношения

Данный модуль является одним из ключевых расширений исходной постановки.

Необходимо отличать аспект от конкретного объекта оценки.

Аспект — характеристика игры, относительно которой выражается мнение.

Объект — конкретная сущность, к которой относится мнение.

Примеры:

- Аспект: персонажи. Объект: конкретный персонаж.
- Аспект: сюжет. Объект: основная сюжетная линия.
- Аспект: игровой процесс. Объект: боевая система.
- Аспект: монетизация. Объект: внутриигровые покупки.

Необходимо предусмотреть извлечение:
- именованных сущностей;
- названий персонажей;
- игровых механик;
- игровых режимов;
- сюжетных элементов;
- других конкретных сущностей, упоминаемых в тексте.

Для реализации допускается использовать NER, семантическое извлечение сущностей и другие подходящие NLP-методы.

Результат должен представлять собой структуру:

Объект → Аспект → Текстовый фрагмент → Тональность.

Если конкретный объект установить невозможно, необходимо сохранять аспект без выдумывания объекта.

### Модуль 7. Определение тональности

Реализовать классификацию тональности:

- положительная;
- отрицательная;
- нейтральная.

Дополнительно предусмотреть возможность смешанной тональности на уровне целого отзыва.

Классификация должна выполняться на двух уровнях:

1. Уровень целого отзыва.
2. Уровень отдельного предложения или смыслового фрагмента.

Для классификации предусмотреть:
- логистическую регрессию;
- SVM;
- подходящую модель на основе BERT.

Для каждого аспекта необходимо определять собственную тональность.

Важно: общая рекомендация Steam не должна автоматически считаться меткой тональности каждого предложения.

Необходимо провести сравнение:
- классификации всего документа;
- классификации отдельных предложений;
- классификации фрагментов, относящихся к конкретным аспектам.

Для обучения и оценки классификаторов предусмотреть ручную разметку выборки.

### Модуль 8. Выявление причин положительной и отрицательной оценки

На основе результатов предыдущих модулей необходимо формировать структурированное представление о причинах пользовательской оценки.

Пример:

Исходный отзыв:
"The game is great, but the latest update ruined the performance. Constant FPS drops make it unplayable."

Результат:

Общая рекомендация: отрицательная.

Аспекты:
- игровой процесс — положительный;
- производительность — отрицательная;
- обновления — отрицательная.

Причины:
- снижение FPS;
- ухудшение производительности после обновления.

Необходимо предусмотреть:
- выявление конкретных причин недовольства;
- выявление причин положительной оценки;
- определение нескольких причин в одном отзыве;
- выявление противоречий между общей рекомендацией и аспектной тональностью;
- сохранение исходных текстовых фрагментов, подтверждающих результат.

Причины должны извлекаться из содержания отзыва, а не генерироваться произвольно.

Если причина не выражена явно, система должна обозначать её как неопределённую.

### Модуль 9. Анализ общей рекомендации и аспектной тональности

Использовать поле recommended как независимый признак общей пользовательской рекомендации.

Необходимо выявлять следующие ситуации:

1. Отрицательная рекомендация и преимущественно отрицательная аспектная тональность.
2. Отрицательная рекомендация и преимущественно положительная аспектная тональность.
3. Положительная рекомендация и преимущественно положительная аспектная тональность.
4. Положительная рекомендация и наличие отдельных отрицательных аспектов.

Особое внимание уделить второй ситуации.

Например, пользователь положительно оценивает практически все составляющие игры, но не рекомендует её из-за конкретной проблемы с монетизацией.

Необходимо рассчитать:
- частоту подобных противоречий;
- наиболее распространённые причины;
- аспекты, наиболее часто встречающиеся в отрицательных рекомендациях;
- аспекты, наиболее часто встречающиеся в положительных рекомендациях.

Необходимо учитывать, что один отзыв может содержать несколько аспектов, поэтому их частоты не должны интерпретироваться как взаимоисключающие доли.

### Модуль 10. Анализ игрового времени

Использовать игровое время как дополнительный аналитический признак.

Предусмотреть следующие условные группы:

- менее 2 часов;
- 2–10 часов;
- 10–50 часов;
- 50–100 часов;
- более 100 часов.

Границы должны настраиваться через конфигурацию.

Провести анализ:
- распределения общей тональности по группам;
- распределения аспектов по группам;
- частоты упоминания технических проблем;
- частоты упоминания игровых механик;
- различий в информативности;
- различий в причинах отрицательных оценок.

При наличии playtime_at_review использовать его в качестве основного признака.

Если доступно только playtime_forever, отдельно обозначить ограничение исследования.

Не использовать игровое время как автоматическую оценку достоверности отзыва.

### Модуль 11. Детекция новых аспектов

Сохранить дополнительное направление из исходного задания.

Реализовать экспериментальную возможность выявления отзывов, содержащих аспекты, не представленные в обучающей выборке.

Предусмотреть:
- One-Class SVM;
- Isolation Forest.

Работать с эмбеддингами текстовых фрагментов.

Оценивать:
- Precision;
- Recall;
- F1-score.

Для оценки необходимо сформировать тестовую выборку с известными новыми или редкими аспектами.

Данный модуль является дополнительным и не должен блокировать реализацию основной функциональности.

Цель:

- фильтрация по информативности;
- кластеризация;
- извлечение аспектов;
- извлечение объектов;
- определение локальной тональности;
- извлечение причин;
- сопоставление с общей рекомендацией;

Результат:
- общая рекомендация;
- аспекты;
- объекты;
- тональность;

- информативность;

## 6. Ручная разметка и оценка качества

Необходимо предусмотреть механизм формирования выборки для ручной разметки.

Рекомендуемый объём — 200–300 отзывов или соответствующих им фрагментов для первоначального эксперимента.

Для каждого размечаемого объекта предусмотреть следующие поля:

1. Общая рекомендация.
2. Информативность.
3. Наличие аспекта.
4. Название аспекта.
5. Конкретный объект, если он присутствует.
6. Тональность аспекта.
7. Причина оценки.
8. Наличие нескольких аспектов.
9. Наличие противоречия между общей рекомендацией и локальной тональностью.

Необходимо предусмотреть экспорт выборки в CSV или Excel и последующую загрузку размеченных данных.

### Метрики

Для классификации тональности:
- Accuracy;
- Precision;
- Recall;
- F1-score;
- Confusion Matrix.

Для кластеризации:
- Silhouette Score;
- ARI при наличии эталонных меток.

Для информативности:
- Precision;
- Recall;
- F1-score.

Для извлечения объектов и аспектов:
- Precision;
- Recall;
- F1-score по вручную размеченной выборке.

Для детекции новизны:
- Precision;
- Recall;
- F1-score.

Для исследования причин оценки:
- доля корректно извлечённых причин на размеченной выборке;
- доля отзывов с установленными причинами;
- частота обнаружения противоречий.

Все метрики должны рассчитываться на отложенной выборке, не участвовавшей в обучении соответствующих моделей.

- Подготовить механизм ручной разметки.
- Реализовать классификатор информативности.
- Оценить качество фильтрации.

Результат: обработанный корпус с оценкой информативности.

- Реализовать TF-IDF.
- Реализовать Word2Vec.
- Реализовать Sentence-BERT.
- Реализовать K-Means.
- Реализовать DBSCAN.
- Подобрать параметры.
- Проанализировать и интерпретировать кластеры.

- Подготовить размеченную выборку.
- Реализовать определение тональности на уровне фрагментов.
- Провести сравнение с базовой классификацией целого отзыва.

Результат: структурированные причины пользовательских оценок.

- Исследовать влияние фильтрации.
- Исследовать особенности смешанной тональности.
- Реализовать детекцию новых аспектов.

Результат: дополнительные экспериментальные выводы.

### Этап 7. Сравнение и формирование результатов

- Сравнить три экспериментальных подхода.
- Рассчитать метрики.
- Построить визуализации.
- Сформировать таблицы результатов.
- Подготовить отчёт для дальнейшего использования при написании научной статьи.

## 12. Ограничения и важные методологические требования

1. Не считать отрицательную рекомендацию Steam эквивалентом отрицательной тональности каждого предложения.
2. Не считать короткие отзывы автоматически неинформативными.
3. Не считать игровое время показателем достоверности мнения.
4. Не исключать отрицательные отзывы только из-за отсутствия конкретной причины.
5. Не придумывать аспекты, объекты и причины, которых нет в исходном тексте.
6. При невозможности извлечь конкретный объект или причину возвращать соответствующее значение как неопределённое.
7. Не считать частоту упоминания аспекта доказательством его причинного влияния на общую рекомендацию.
8. Сохранять оригинальные отзывы и возможность проверки результатов по исходным фрагментам.
9. Разделять автоматически полученные результаты и результаты ручной разметки.
10. Не допускать утечки информации между обучающей и тестовой выборками.

## 13. Ожидаемый итог разработки

По завершении разработки должна быть получена экспериментальная программная реализация комбинированного подхода к аспектному анализу тональности отзывов Steam.

Результаты должны позволять:

- определять общую рекомендацию игры;
- выявлять отдельные аспекты пользовательских оценок;
- извлекать конкретные объекты эмоционального отношения;
- определять положительную, отрицательную и нейтральную тональность каждого аспекта;
- выявлять причины пользовательского недовольства и удовлетворённости;
- обнаруживать случаи, когда отрицательная рекомендация обусловлена отдельной проблемой при общей положительной оценке игры;
- отделять информативные отзывы от малоинформативных;
- исследовать взаимосвязь между игровым временем и содержанием отзывов;

- сравнивать эффективность разных методов анализа.

Главный результат исследования — экспериментальная проверка того, что комбинированный аспектный анализ позволяет получить более детальное и содержательное представление о пользовательском мнении, чем традиционная классификация тональности всего отзыва.
